# HStack v0.2 design

Optional hooks into Hermes, and an optional handoff to another stack. A default install still adds no hooks and no external route. The idle index stays the twelve description rows plus the `hstack` category header.

Measured with the existing checker, `scripts/check_skills.py`, which uses Hermes's estimator `ceil(utf-8 bytes / 4)` (`estimate_tokens_rough` in `agent/model_metadata.py`). The target is the v0.1 figure of 204, and the hard ceiling is 230.

## Hooks that earn a place

Hermes has four hook systems. Gateway hooks (`~/.hermes/hooks/*/HOOK.yaml`) do not run in the CLI. Python plugins load only after `plugins.enabled` and call `ctx.register_hook` inside the process. Shell hooks are a `hooks:` list in the profile `config.yaml`, spawned as a subprocess, and they run in the CLI, gateway, Desktop, TUI, and dashboard chat. That is the mechanism these shims use. HStack does not register a plugin, does not set `plugins.enabled`, and does not set `hooks_auto_accept`.

Each installed hook is a few lines that call `hooks/hstack_hook.py`. The skills do not import it. Uninstalling the hooks leaves the skills working.

Hermes still asks the first time it sees each `(event, command)` pair and stores the answer in `~/.hermes/shell-hooks-allowlist.json`. The installer does not write that file. A gateway, cron job, or other non-interactive surface will not run a new hook until that prompt has been answered, or until the user passes `--accept-hooks` / `HERMES_ACCEPT_HOOKS=1` themselves. Editing the script later does not clear the allowlist. Hermes keys it on the command string (`hermes hooks doctor` reports mtime drift).

`--with hermes-hooks` installs all three. A subset is `hermes-hooks-guard`, `hermes-hooks-save`, or `hermes-hooks-suggest`. The installer copies the shims to `$HERMES_HOME/hstack/hooks/`, edits `config.yaml`, and copies `apply_hooks.py` beside the addon script so a later `curl | sh -s -- --uninstall` can remove them. It backs up `config.yaml` to `$HERMES_HOME/hstack-backups/` before a change. Uninstall removes `$HERMES_HOME/hstack/` and leaves that backup directory in place. A second run that would write the same block does not write and does not take another backup. `--uninstall` removes only the entries marked `# hstack:<id>` and the files this installer wrote. Another product's hook stays.

### `guard` — `pre_tool_call` on `terminal`

`pre_command` is in `VALID_HOOKS`, and it fires before a recognized slash command. The same entry says returns are ignored in v1. It cannot block `rm`. The hook that can block a tool is `pre_tool_call`. A shell hook selects the tool with `matcher`, and `fail_closed: true` is honored only on `pre_tool_call`.

The guard matches `terminal` and fails closed. It blocks a short list that matches the safety playbook's destructive case: `rm -rf` of `/`, `/*`, `~`, or `$HOME`; `mkfs`; `dd` onto a disk device; a fork bomb; `shutdown`, `reboot`, `poweroff`, or `halt`. It does not try to be the write sandbox. Hermes already has `approvals.mode`, the command blocklist, and the write boundary. The playbook tells the agent not to install a hook by itself. This one is only the installer flag.

There is no separate "pre-command safety" event that can block. Using `pre_command` here would be a comment, not a guard.

### `save` — `on_session_finalize`

`on_session_end` is the wrong event for "session end". The catalog says it fires at the end of every `run_conversation()` call, and again from the CLI exit handler if a turn was in flight. Its return is ignored. `on_session_finalize` fires when the CLI or gateway tears down the session (`/new`, quit, gateway reset or shutdown). That is the session boundary.

The shim appends one line to `$HERMES_HOME/hstack/session-log.tsv`: time, session id, platform. It does not write the message. The memory playbook may read the last line when the file exists, and it does nothing when the file is absent. The skills do not require the hook.

`on_session_finalize` can also return a `message` for the user. This shim returns `{}` so it does not talk over the session.

### `suggest` — `pre_llm_call`

Nothing in `VALID_HOOKS` is a "suggest a skill" event. `on_session_start` and `on_skill_lifecycle` are observers. Their returns are not injected. `pre_llm_call` runs once per user turn, before the tool loop, and a `{"context": "..."}` return is appended to that turn's user message. It is not part of the cached system prompt, so it is not idle-index cost.

The shim injects one line, and only when `extra.is_first_turn` is true, the message does not already name an HStack skill, and a keyword maps to one playbook. It names `references/<file>.md`. It does not name another stack, and it does not load one. Later turns pay nothing. If the field is missing, it injects nothing.

## External stacks

The router picks an HStack playbook first (`references/routes.md`, then one playbook). Only then does it load `references/stacks.md`. That file is not an index row, so the idle count does not move. The route upper bound in `PARITY.md` includes it, because the router loads it.

`stacks.md` is the registry. A fenced JSON block is what `hstack_stack.py` reads. Each entry has what the stack is for, how to detect it without running it, the license, the pinned commit, the sha256 of the codeload archive, and the archive URL. Detection does not execute the other project:

- **gstack.** A `SKILL.md` under `${HERMES_HOME:-~/.hermes}/skills/gstack/`, or the file `~/.claude/skills/gstack/bin/gstack-state-root.sh` (the same file is also checked under `~/.codex/skills/gstack/bin/`). Those paths are from `docs/hosts.md` and `docs/install.md` at the pinned gstack commit. `~/.gstack` is state (`docs/state-root.md`, `GSTACK_HOME`). It is not treated as an install. The marker script is not run.
- **pstack.** A file whose path ends in `skills/poteto-mode/SKILL.md` under `~/.cursor/plugins` or `~/.claude/plugins`, searched a few directories deep and not through symlinks. That is the file `pstack/agents/poteto-agent.md` tells a subagent to find. Install is `/add-plugin pstack` in Cursor, or the Claude marketplace command in `pstack/README.md`. There is no standalone pstack repository. The pin is `cursor/plugins` at the commit in `RESEARCH.md`.
- **tstack.** One directory contains both `leaving-pr-comments/SKILL.md` and `sol-loop/SKILL.md`. The roots are `~/.claude/skills`, `~/.codex/skills`, `~/.agents/skills`, and the Hermes skills directory. The README at the pinned commit installs with `cp -R tstack/skills/*` into the Claude or Codex skills directory. A clone anywhere else is not detected.
- **gbrain.** `config.json` under the directory `configDir()` returns. In `src/core/config.ts` at the pinned commit, `GBRAIN_HOME` is a parent and the code appends `.gbrain`. Unset, the file is `~/.gbrain/config.json`. An `mcp_servers.gbrain` entry in the Hermes `config.yaml` also counts. A `gbrain` binary on `PATH` does not. Their Hermes page (`docs/mcp/HERMES.md`) registers `gbrain serve`. This design does not run that, and it does not add the MCP server. Scaffolded skill trees are not scanned outside the roots above. `gbrain-upgrade/SKILL.md` next to `brain-ops/SKILL.md` under those roots counts, because `skills/manifest.json` ships both.

A receipt at `$HERMES_HOME/hstack/external/<id>/<commit>/.hstack-external` also counts. That tree is produced only by the install command below. It is not copied into `skills/hstack`, and it is not added to `skills.external_dirs`. Adding it there would put the other stack in the idle index. GStack's Hermes host is 1,182 idle tokens in `PARITY.md`.

The router suggests at most one stack. It prefers an installed stack when that stack fits the task better than the playbook already loaded. One line, name and why, then a question. Nothing from that stack is loaded until the user says yes. If none of the installed stacks fit, it may name one that is not installed and show the install command. It still waits for a yes. A no is `decline`, stored for that session id under `$HERMES_HOME/hstack/declines/`. Detect hides a declined id from the suggestion. The session id is whatever the agent passes. Hermes does not give this script a session id of its own.

HStack never fetches a stack on its own. `install` without `--yes` exits before any network call. `--yes` is the user's yes for that session, and the command refuses a session that has already declined. The download is the pinned archive URL. The sha256 in the registry is checked before extract, the same gate as `install.sh` against `/dl/hstack.tar.gz.sha256`: magic bytes, digest match, no absolute member, no `..`, no link. A mismatch deletes the temp file and writes nothing. The extract directory is `$HERMES_HOME/hstack/external/<id>/<commit>/`. The script does not run the other project's setup. Setup would copy skills into the Hermes index and, for gstack, can download a browser. Hand off means printing the path and stopping.

Their own text is not committed in this repo. The registry records the pin, the checksum, the license line, and a one-line description written here.

## Consent is a check, not a paragraph

`scripts/check_consent.py` fails the build if any HStack skill or playbook other than `references/stacks.md` contains an external archive URL, an `hstack_stack.py install` invocation, or a `skill_view` of a skill this repo does not own. `stacks.md` must say "at most one", must say "until the user says yes" before the install command, and must mention `decline` and `--yes`. The hook sources are scanned for the same archive URLs. The script's own tests cover a playbook that loads an outside skill with no question, and an install line with no yes. Those strings are not files in the tree.

The install command also refuses to download without `--yes`. Both gates have to hold.

## Installer version

Skill frontmatter, `VERSION`, and the archive name move to 0.2.0. `HSTACK_VERSION=0.1.0` still requests `/dl/hstack-v0.1.0.tar.gz`. The site build copies the bytes already published at that URL (sha256 `0c8009ee04fb31126b76e4202c91eee14e8d5be7d1cd42ac0cee551012eeda6e`) and does not rebuild them. The latest alias `/dl/hstack.tar.gz` becomes the 0.2.0 archive. `/dl/hstack-v0.2.0.tar.gz` is the pinned name. Cache for the two versioned archives is immutable. The alias stays a five-minute cache, which is the existing rule, because its bytes change on this release.

## What stays out

No Python plugin. No `hooks_auto_accept`. No edit to `plugins.enabled`. No MCP server for gbrain. No copy of another stack's `SKILL.md`. No automatic `skills.external_dirs` entry. The default `install.sh` path does not write `hooks:`.
